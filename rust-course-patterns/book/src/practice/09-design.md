# 패턴을 읽기 쉽게 고치기

패턴을 사용하면 여러 조건을 짧게 표현할 수 있습니다. 그러나 코드가 짧다고 해서
뜻도 분명한 것은 아닙니다. 패턴을 작성한 뒤에는 다음 두 가지를 확인해야 합니다.

1. 코드의 모양만 보고 어떤 값과 매칭되는지 알 수 있는가?
2. 조건이 나타내는 업무 규칙을 이름만 보고 알 수 있는가?

첫 번째 질문에 답하기 어렵다면 흩어진 조건을 하나의 패턴으로 모읍니다. 두 번째
질문에 답하기 어렵다면 긴 패턴을 의미가 드러나는 함수로 나눕니다.

## 흩어진 조건을 하나의 패턴으로 모으기

다음 함수는 입력값이 있고, 작업이 성공했으며, 시도 횟수가 1부터 3까지인지
차례로 확인합니다.

```rust
{{#rustdoc ../../../examples/09_design.rs item=retry_nested_if}}
```

세 조건이 중첩된 `if let`과 `if`에 흩어져 있어 어떤 입력에서 `true`가 되는지
한눈에 파악하기 어렵습니다. 반환값으로 참인지 거짓인지만 필요하므로 `matches!`로
조건을 한곳에 모을 수 있습니다.

```rust
{{#rustdoc ../../../examples/09_design.rs item=retry_one_match}}
```

`Some(Ok(1..=3))`은 바깥에서 안쪽으로 다음 세 조건을 그대로 보여 줍니다.

- 값이 `Some`입니다.
- 작업 결과가 `Ok`입니다.
- 성공한 값이 `1..=3` 범위에 들어갑니다.

이처럼 내부 값을 이후 코드에서 사용하지 않고 매칭 여부만 필요할 때는
`matches!`가 알맞습니다. 성공한 값을 꺼내 후속 처리에 사용해야 한다면 `if let`,
`let else`, `match`로 값에 이름을 붙입니다.


이 조건은 구조체 패턴, OR 패턴, 범위 패턴을 조합해 한 번에 표현할 수 있습니다.

조건이 짧고 이 함수에서만 사용된다면 이 형태로도 충분합니다. 어떤 상태와 실패
횟수를 허용하는지 패턴에 모두 드러납니다.

## 업무 규칙에 이름 붙이기

시작 가능한 상태를 다른 곳에서도 판단해야 한다면 긴 패턴을 계속 반복하지 않고
그 규칙에 이름을 붙입니다.

```rust
{{#rustdoc ../../../examples/09_design.rs item=can_start..should_retry_after}}
```

`can_start`는 상태 규칙을, `should_retry_after`는 상태와 실패 횟수를 합친 재시도
규칙을 나타냅니다. 호출하는 코드는 구조체의 구체적인 모양보다 판단의 뜻을 먼저
읽을 수 있습니다.

```rust
{{#rustdoc ../../../examples/09_design.rs item=use_rules}}
```

실패 횟수가 2인 일시 정지 작업은 재시도 조건을 만족하므로 상태가 `Running`으로
바뀝니다. 실행 중인 작업에는 `can_start`가 `false`를 반환하므로 같은 작업을 다시
시작하지 않습니다.

## 패턴을 검토하는 순서

패턴을 작성하거나 고칠 때는 다음 순서로 판단하면 됩니다.

1. **값이 필요한가?** 매칭 여부만 필요하면 `matches!`를 사용합니다. 내부 값이
   필요하면 `match`, `if let`, `let else`로 바인딩합니다.
2. **조건이 흩어져 있는가?** 중첩된 조건이 값의 구조를 차례로 검사한다면 하나의
   패턴으로 모읍니다.
3. **패턴만 보고 뜻을 알 수 있는가?** 업무 규칙이 가려진다면 작은 함수로 나누고
   뜻이 드러나는 이름을 붙입니다.
4. **모든 경우를 처리해야 하는가?** 열거형의 변형을 빠짐없이 처리해야 한다면
   `_`로 나머지를 숨기지 말고 각 변형을 적습니다.
5. **값을 다시 사용하는가?** 바인딩이 값을 이동하는지 참조를 빌리는지 확인하고,
   같은 값이 다시 필요하면 `@` 바인딩이나 참조를 사용합니다.

좋은 패턴은 가장 짧은 패턴이 아니라, 처리할 값의 모양과 코드가 판단하는 규칙을
함께 드러내는 패턴입니다.
