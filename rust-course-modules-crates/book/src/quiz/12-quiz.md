# 패키지·크레이트·모듈 퀴즈와 풀이

각 문제에서 가장 알맞은 답을 하나 고르세요. 먼저 여덟 문제를 모두 푼 뒤
[정답과 풀이](#정답과-풀이)에서 판단 근거를 확인합니다.

## 문제

### 1. 패키지와 크레이트

`Cargo.toml` 하나가 라이브러리<sub>library</sub>와 실행 파일 두 개를 관리하는 패키지<sub>package</sub>가
있습니다. 이를 올바르게 설명한 것은 무엇인가요?

- ① 패키지 세 개와 크레이트<sub>crate</sub> 하나입니다.
- ② 패키지 하나에 라이브러리 크레이트 하나와 실행 파일 크레이트 두 개가 있습니다.
- ③ 모듈<sub>module</sub> 하나만 존재합니다.
- ④ 워크스페이스<sub>workspace</sub>가 없으면 실행 파일을 둘 수 없습니다.

### 2. 모듈과 파일

`mod parser;` 선언의 역할로 가장 알맞은 것은 무엇인가요?

- ① `parser`를 외부 크레이트로 내려받습니다.
- ② 모듈 트리에 `parser`를 연결하고 해당 모듈의 코드를 찾게 합니다.
- ③ `parser` 안의 모든 항목을 자동으로 공개합니다.
- ④ 새 패키지를 만듭니다.

### 3. 경로와 `use`

크레이트 루트<sub>crate root</sub>에서 시작하는 절대 경로를 나타내는 접두사는
무엇인가요?

- ① `self::`
- ② `super::`
- ③ `crate::`
- ④ `extern::`

### 4. 공개 범위

외부 크레이트에는 숨기고 현재 크레이트 안에서는 여러 모듈이 사용하게 하려면 어떤 공개
범위가 가장 알맞은가요?

- ① `pub`
- ② `pub(crate)`
- ③ `private`
- ④ `pub(extern)`

### 5. 라이브러리와 실행 파일

같은 패키지의 `src/main.rs`에서 `src/lib.rs`의 공개 API를 사용하는 방식으로 가장
알맞은 것은 무엇인가요?

- ① 라이브러리 소스 파일을 `include!`로 복사합니다.
- ② 패키지의 라이브러리 크레이트 이름으로 공개 API를 가져옵니다.
- ③ 모든 함수를 `main.rs`에 다시 작성합니다.
- ④ 비공개 항목을 파일 경로로 직접 호출합니다.

### 6. 재공개

깊은 내부 모듈의 공개 타입을 크레이트 루트에서 사용하게 하는 선언은 무엇인가요?

- ① `pub use internal::Type;`
- ② `mod use internal::Type;`
- ③ `extern Type;`
- ④ `crate Type;`

### 7. 워크스페이스

여러 패키지를 워크스페이스로 묶는 주된 이점으로 가장 알맞은 것은 무엇인가요?

- ① 모든 패키지가 하나의 크레이트가 됩니다.
- ② 공통 명령과 잠금 파일로 여러 패키지를 함께 관리할 수 있습니다.
- ③ 모듈 공개 범위가 자동으로 모두 열립니다.
- ④ 크레이트 사이의 의존성 선언이 필요 없어집니다.

### 8. 모듈 경계 설계

변경 가능성이 큰 저장 방식이 공개 API 곳곳에 드러나 있습니다. 가장 알맞은 개선은
무엇인가요?

- ① 모든 모듈과 필드를 `pub`으로 바꿉니다.
- ② 내부 구현을 비공개 모듈에 두고 필요한 동작만 공개 API로 드러냅니다.
- ③ 파일을 하나로 합치고 모든 이름을 짧게 바꿉니다.
- ④ 외부 사용자가 내부 경로에 직접 의존하게 합니다.

## 정답과 풀이

### 1. 정답: ②

패키지는 `Cargo.toml` 하나가 관리하는 단위입니다. 라이브러리와 각 실행 파일은
각각 별도의 크레이트로 컴파일됩니다.

### 2. 정답: ②

`mod parser;`는 현재 크레이트의 모듈 트리에 `parser` 모듈을 선언합니다. 파일 배치는
코드를 찾는 방법이며 공개 범위는 각 항목의 `pub`으로 별도로 정합니다.

### 3. 정답: ③

`crate::`는 현재 크레이트의 루트에서 경로를 시작합니다. `self::`는 현재 모듈,
`super::`는 부모 모듈에서 시작합니다.

### 4. 정답: ②

`pub(crate)`는 현재 크레이트 안에서만 항목을 공개합니다. 외부 크레이트의 API에는
노출하지 않으면서 내부 모듈끼리 공유할 수 있습니다.

### 5. 정답: ②

패키지 안의 실행 파일 크레이트도 라이브러리 크레이트의 외부 사용자처럼 공개 API를
사용합니다. 구현을 복사하지 않으므로 라이브러리 동작을 한곳에서 관리할 수
있습니다.

### 6. 정답: ①

`pub use`는 항목을 현재 경로에서 다시 공개합니다. 내부 파일 배치를 바꾸더라도
사용자가 같은 공개 경로를 계속 쓰게 할 수 있습니다.

### 7. 정답: ②

워크스페이스는 여러 패키지에 명령을 함께 실행하고 같은 `Cargo.lock`과 `target/`
디렉터리를 공유하게 할 수 있습니다. 각 패키지와 크레이트의 경계는 그대로
유지됩니다.

### 8. 정답: ②

변경 가능성이 큰 구현을 비공개로 감추고 필요한 약속만 공개하면 내부 구조를
바꾸더라도 외부 사용자의 코드를 덜 깨뜨립니다.
